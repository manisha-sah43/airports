# Provenance — vendored data & code

This asset is self-contained: it never imports from `shared/` or reads sibling
project folders at run time (verified — zero `shared/` imports anywhere in
`scripts/`). Everything below was **snapshotted** from the canonical sources. Per
Claude Code repo rule #4, the canonical copies stay authoritative — any fix lands
there first, then is re-vendored here.

Snapshot date of the curve-side data: **2026-05-12** (the `run_dt` in routes.json).
The asset now ships **both halves** of the pipeline: the route-generation stage
(`scripts/routegen/`, "front half") that builds `routes.json` from the vendored
demand snapshot, and the consumer that turns curves + quality targets into the
BPO observation list ("back half"). Generation is off by default (the pipeline
consumes the vendored snapshot); enable it via `regenerate_routes` — see below.

## Regenerating the vendored data (now in-asset)

The route-generation stage lives inside the asset, so refreshing the curves no
longer means hand-copying from a project folder.

**Rebuild curves from the vendored demand snapshot** (offline, no warehouse):
set `regenerate_routes: true` in `inputs/config.json` (or pass
`--regenerate-routes`) and run. `regenerate_scope` picks `"targets"` (just the
airports in `targets.csv`, fast) or `"all"` (every airport). Output goes to
`config/routes_<demand_snapshot_date>/` + `config/demand_lut_<demand_snapshot_date>/`.
Verify it still matches the shipped snapshot with
`./.venv/bin/python scripts/verify_routegen_parity.py`.

**Latent gap in the shipped curves (reproduced by default).** The original
dashboard route-builder only had coords for 15 hub airports, so it skipped the
airport-terminal hex exclusion for the other ~178 airports; the LUTs (complete
coords) excluded it for all 193. The generator reproduces this as-is by default
(`verify_routegen_parity.py` → 193/193 on both). To rebuild the curves *with* the
exclusion applied everywhere (the correction — changes ~178 airports' curves), set
`regenerate_full_exclusion: true` alongside `regenerate_routes: true`. This is
opt-in only; leaving it false keeps parity with the published snapshot.

**Refresh the demand snapshot itself** (needs warehouse access): re-pull
`scripts/queries/airport_session_demand_emea.sql` (and `airport_metadata.sql` for
coords) via QueryRunner, overwrite `config/demand_<new_date>/emea_demand_full.csv`
(+ the obs CSV), bump `demand_snapshot_date`, then regenerate as above.
